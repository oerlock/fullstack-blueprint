# 项目目录结构规范

## 1. 设计原则

- **模板独立**：每个 `templates/vN/` 都是一份完整、独立、可直接使用的项目模板。
- **按需拆分**：优先保持简单，随着业务复杂度渐进式拆分。
- **职责清晰**：目录和模块应有明确职责，避免过度抽象。
- **独立演进**：不同代际的模板可以采用不同的目录结构，不强制保持兼容。

## 2. 仓库目录结构

```text
fullstack-blueprint/
├── templates/                 # 全栈项目模板
│   ├── v1/                    # 第一代模板
│   ├── v2/                    # 第二代模板
│   └── ...
├── docs/                      # 仓库文档
│   ├── standards/             # 工程规范
│   └── README.md
├── scripts/                   # 仓库维护脚本（按需创建）
├── .github/                   # GitHub 配置
├── .gitignore
├── LICENSE
└── README.md
```

## 3. 模板目录约定

每个 `templates/vN/` 都是一份完整的项目模板，其内部目录由对应代际的技术栈和工程架构决定。

约定：

- 前端、后端及相关工程配置统一放在对应模板目录内。
- 模板专属文档放在对应模板目录内。
- 模板内部可以根据实际需要组织目录，不强制不同代际采用相同结构。
- 已发布的模板原则上保留，后续架构调整通过新代际体现。

## 4. 目录维护约定

1. 只有存在明确职责和实际需求时才新增目录。
2. 模块简单时，不必提前拆分子目录。
3. 通用能力放在公共目录，业务专属能力留在对应模块内。
4. 避免为了追求目录对称而创建空目录。
5. 目录结构随项目复杂度演进，不要求一次性设计完整。
